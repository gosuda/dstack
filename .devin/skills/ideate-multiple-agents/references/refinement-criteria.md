# Refinement and evaluation criteria

Use this rubric during Evaluate and Converge. No criterion fits every idea; judge which dimensions matter for the context at hand.

## Core evaluation dimensions

### 1. User value

The most important dimension. When value is unclear, nothing else matters.

Painkiller against vitamin: a painkiller solves an acute, frequent problem. Users seek it, switch for it, describe it with emotion, and built workarounds. A vitamin is nice to have. Users nod politely and do not change behavior.

Questions to ask:

- Name three specific people with this problem right now.
- What do they do today instead. The real competitor is the current workaround.
- Would they switch from their current approach, and what would make them switch.
- How often they hit the problem. Daily problems outweigh monthly ones.
- Whether this is a pull problem users ask for or a push problem they are told to want.

Red flags: everyone could use this without a named user, like X but better with only marginal gain, or a real but rare problem with intensity but no frequency.

### 2. Feasibility

Technical feasibility: whether the core technology exists and works reliably, the hardest technical problem and whether it is known-hard or novel, dependencies on third parties or data outside control, and the minimum technical stack.

Resource feasibility: minimum team and effort for an MVP, required specialized expertise, and regulatory, legal, or compliance needs.

Time to value: how quickly something reaches users, whether a days-or-weeks version exists, the critical path, and what must happen first.

Red flags: a very hard research problem must be solved first, multiple dependencies must all work at once, or the MVP still needs months of work.

### 3. Differentiation

Questions to ask: how a user would describe this to a friend and whether that sounds compelling, the one thing nothing else does, whether that edge survives copying, and whether the difference matters to users rather than only to builders.

Types from strongest to weakest: new capability that was previously impossible, tenfold improvement on a key dimension that changes behavior, new audience previously excluded, new context where existing solutions fail, better experience for the same capability, and lower cost alone.

Red flags: differentiation lives only in technology, claims of faster or cheaper without a structural reason, or the differentiating feature is not the feature users care about most.

## Assumption audit

For every idea direction, list assumptions in three categories.

- Must Be True and dealbreakers: when wrong, the idea fails entirely. These need validation before building.
- Should Be True and important: when wrong, the approach changes but the core can still work.
- Might Be True and nice to have: secondary features or growth bets. Do not validate until the core is proven.

## Decision framework

Rank on this matrix, then use differentiation as the tiebreaker in the same quadrant.

- High feasibility with high value: do this first.
- Low feasibility with high value: worth the risk.
- High feasibility with low value: only when trivial.
- Low feasibility with low value: do not do this.

## MVP scoping principles

- One job, done well. The MVP nails exactly one user job, not three jobs partially.
- The riskiest assumption first. The MVP primary purpose is to test the assumption most likely to be wrong.
- Time-box, not feature-list. Ask what can be built and tested in the timeframe.
- The Not Doing list is mandatory. Name what is cut and why. This prevents scope creep and forces honest prioritization.
- When the first version feels embarrassing to the builder, the scope is about right. Over-built MVPs wait too long.
