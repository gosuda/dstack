# Putting a jumbled list back in order

Some catalog, index, table of contents, enum, or menu drifts until its order is arbitrary. This skill puts that one listing back under a single stated principle: related items sit together, clusters follow the principle, and every word stays exactly as it was.

## When this fits, and when it does not

Reach for it when the user says reorder this, or when a listing's order clearly went arbitrary and needs a sensible pass. Name the principle before moving anything: the user's own words win, then whatever the existing sequence was reaching for, then a default such as workflow sequence, dependency order, grouping by kind, severity, frequency, or alphabetical order.

Stay out when the ranking is the point. Listings with intentionally ranked items are not this job; this skill does not preserve explicit ranks, so it does not touch them. Likewise, rewording, adding, or removing content is refused: items are moved only. Remote, credential, publish, deploy, or irreversible changes are refused too. This skill writes only the named local artifact, and version control is the rollback path.

## What you start with

Only two things: the listing, either supplied or identified from context, and the one principle. Pin the listing first: identify the ordered set in focus and count the items so the full scope is established before anything moves. Then confirm every item belongs in this scope, and note any mirrored copies that must carry the identical order.

## Work the list in place

Keep related items adjacent first, then order the clusters by the stated principle, keeping the order inside each cluster as it was. Never blend two incompatible sorts to force a tidy look. Move items in place without rephrasing labels, descriptions, or metadata, and carry the identical order to every mirrored copy. A pass that finds nothing to improve changes nothing.

The work is done when the reader can name the ordering principle, every item is still present, kin are adjacent, and mirrored copies carry the identical order, or when the original stands unchanged because nothing needed reordering.

## If the list will not cooperate

An unclear listing boundary or item set stops the work: ask the user to identify or supply the exact target. A set of mixed item types with no shared ordering principle stops it too: ask which subset to reorder or which principle to apply. When the principle itself is unknown, surface the best guess and wait for explicit confirmation before proceeding. When the principle fits some items but not all, sequence the compatible subset and note the remainder as out of scope.

If a reposition corrupts or loses content, restore from version control. The working tree is the only mutation surface, and its history is the way back.
