# Open source adoption

Plan how an open-source project earns users and contributors: a README a newcomer can actually follow, a funnel with real entry points, onboarding a small team can sustain, an ordered launch, and honest maintenance expectations. Every health claim traces to repository facts. Nothing here fabricates metrics.

This skill is read-only planning in chat. It makes no repository or remote changes. It never trades in fake stars, coordinated upvotes, fabricated downloads, astroturfing, automated release promotion, or contributor quotas. The funnel is earned step by step: user, star, issue, pull request, regular contributor, maintainer.

## What you need

- `repo` (required): the project with its actual current state (README, license, contributing docs, issue and pull request posture).
- `capacity` (optional): maintainer time available. When omitted, plan to a low sustainable band.

## Walk the newcomer path

Assess the README and quickstart the way a first-time contributor experiences them: install, run, change one thing. Give each walk step a pass or gap finding with the path cited. Map the contributor funnel through its real entry points (good first issues, docs fixes, discussion venues, the review turnaround the team can sustain), so each stage names its real pathway or its absence.

## Fit the plan to the team

Design issue and pull request onboarding (templates, labels, response expectations) that the stated capacity can meet. State maintenance expectations honestly: cadence, support scope, and named sunset signals, with promises kept inside capacity. When capacity is too thin for the ambition, cut the plan to the sustainable core and name the cut. License or health claims that cannot be verified are marked unknown, never asserted as a clean bill of health.

## Sequence the launch, measure what exists

Plan the launch sequence as an ordered list of surfaces, each with readiness criteria and what must be true before it, and never through coordinated voting or brigade behavior. Set value metrics only from observable facts the team already measures (merges from newcomers, time to first contribution, docs-driven arrivals), with each metric naming its existing measurement source.

## What you hand back

An adoption plan in chat: README and quickstart findings, the contributor funnel with real pathways, issue and pull request onboarding, the launch sequence with readiness gates, maintenance expectations, and value metrics.
