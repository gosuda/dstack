# GitHub solution research

Something is broken or blocked and the answer may already exist on GitHub: a maintainer confirmed issue, a merged fix, a released patch, an official example, or a project that solves the problem outright. This skill profiles the local problem first, then searches GitHub for evidence, ranks what it finds by problem fit, and translates the best match into local work with minimal adaptation.

This skill is read only. It writes no files, changes no version control state, touches no credentials, and mutates nothing remote. It runs `gh` searches, reads local code, logs, and config, and may spawn read only research subagents. Its output is a chat report: a recommendation with reuse, adapt, and avoid guidance, a verification command, and an honest confidence label when the evidence is weak.

## Profiling the problem locally

Capture the goal, the symptom or error signature, the reproduction path, versions, runtime, dependency and framework names, recent changes, constraints, and attempted fixes. Inspect local files and logs to fill every discoverable fact before asking the user for anything. Do not inspect private repositories unless the user explicitly scopes and authorizes that access; without that authorization, private repos are out of scope.

For a reported defect, state the symptom in one sentence and search open and closed tracker evidence with distinct framings before reconstructing a root cause. Vary the surface, the observed failure, the trigger, and the workaround rather than repeating synonyms alone. Read the actual closure explanation, since closed as not planned says nothing about the cause. A hit counts as a duplicate only when its mechanism and applicability match the incident, not merely its symptom. Inspect linked fix PRs, their merge and release state, and the current checkout's relevant consuming path, since an unchanged line alone never proves the user's build executes that path. On a match, report the issue, the mechanism with current path and line evidence, the fix state, and the incident evidence connecting them, and leave unexplained parts of the report explicitly unconfirmed. Treat advisory diagnoses as hypotheses to compare against the consuming code and the existing contract, not as authority.

## Choosing how to search

Pick the evidence mode from the problem type: for errors and regressions, search issues, PRs, releases, and code first; for capability or tool needs, search repository candidates first; for feature implementation, use both.

Then decide whether read only research subagents would improve breadth, evidence quality, or review coverage. Use them when the problem spans 2 or more independent ecosystems, repository discovery needs broad candidate coverage, evidence splits cleanly by project, version, or surface, or the final recommendation would benefit from independent review. Skip them for narrow single surface errors, when local context must be understood before external research, or when rate limits, private repositories, secrets, or sensitive logs make delegation risky. State the reason when subagents are skipped. Never pass tokens, cookies, private repository contents, sensitive logs, secrets, production data, or credentials to subagents.

## Searching and ranking

Build targeted searches from exact error text, package and API names, version numbers, framework plus symptom, file names, config keys, stack trace fragments, failing command names, or capability plus framework, runtime, and API names. Start narrow, then add constraints (version, language, platform, deployment target, bundler, database, auth provider, runtime).

Use the GitHub CLI as the default search and inspection surface: `gh search repos`, `gh search issues`, `gh search prs`, `gh search code`, `gh repo view`, `gh issue view`, `gh pr view`, and `gh api`, before browser scraping or custom scripts. Adjust query, repo, fields, and limits to the local problem. Run `gh auth status` only when a command fails with 403, 429, a private repository authorization error, or an explicit not authenticated message; inspect the emitted rate limit or authorization context before retrying, reducing breadth, or switching endpoints. Never paste or persist tokens, cookies, private repository contents, or credentials in prompts, files, logs, or memory.

Search evidence surfaces in priority order when relevant: issues, PRs, and discussions; merged fixes; release notes and changelogs; examples and templates; source code; then repository level candidates. For implementation blockers without an error, search the desired capability plus framework, runtime, and API names. For public platform data needs (trends, hot lists, topic search, engagement metrics), check reusable public endpoints, open source crawlers, archived datasets, and API field evidence before browser scraping; verify the chosen source with a minimal real request and keep anonymous hot list data separate from logged in search and topic data.

Record candidate projects with Stars, forks, language, license, activity, and basic content. Prefer high fit, high Star, active, non archived repositories with clear licenses and real examples, and lower the Star threshold when the high Star set is too broad or misses the exact problem. Rank by problem fit first: maintainer confirmed issues, merged PRs, released fixes, official examples, and exact matching code beat popular adjacent projects, with Stars and forks only as supporting maturity context and tie breakers among similarly fitting repositories. Demote matches that are old, version mismatched, archived, unresolved, speculative, or based only on user guesses. For security, auth, payments, infrastructure, or production operations, cross check findings against current official docs or repositories when facts may have changed.

Deep read the strongest projects and evidence. For each serious item pin down the exact match (same error, behavior, API, version, environment, workflow), the evidence strength (maintainer confirmation, merged PR, released fix, reproducible code example, test fixture, repeated independent reports), the applicability (conditions that must match locally), the implementation value (patch, config, API usage, dependency version, workflow, test, operational pattern), and the risk (stale version, unresolved issue, unsafe workaround, license concern, security or privacy impact, deployment mismatch, overbroad change).

When subagents were used, define each one's query family, repository scope, evidence surface, constraints, allowed write scope, and expected output; require direct links, verified metadata, problem fit rationale, risk notes, and explicit rejection reasons; keep them read only; merge and deduplicate results before ranking (repeated reports of the same issue, PR, code path, or repository never count as independent evidence); and directly verify the strongest claims with `gh`, source reads, tests, logs, real requests, or official docs before finalizing.

Translate to local work with minimal adaptation. Prefer the existing GitHub solution's public workflow, API, or architecture, and adapt only the parts the user's local interfaces, configuration, data or auth model, deployment target, or language and runtime require. Prefer reading patterns and reusing existing public interfaces over copying code; when code reuse is necessary, check the license and keep attribution and obligation risks visible. Avoid large rewrites of an existing GitHub solution and large verbatim excerpts from repositories, READMEs, issues, PRs, or documentation. When evidence is weak, say so: mark the recommendation first principles or local only with a confidence label instead of stretching weak matches into a confident recommendation.

## What you hand back

A report holding the local problem profile (goal, symptom or error, versions and environment, local constraints); the search path (queries or discovery methods used, GitHub surfaces searched, whether subagents were used or skipped and why); a subagent trace when subagents were used (each subagent's scope, evidence surfaces, key findings, rejected candidates, deduplication results, and which claims were directly verified); project candidates when a GitHub project is relevant (repo link, Stars, forks, language, license, activity, basic content, match rationale, local use) in a compact table; key evidence (links to issues, PRs, code, examples, releases, or repos, with match rationale); the recommended solution (what to reuse directly, what to adapt locally, what to avoid copying, and why it fits); rejected or risky options with reasons; the verification standard (test, build, reproduction command, real request, or manual check required to confirm the fix); and a confidence label when evidence is weak or no strong GitHub solution was found. For website, SaaS, landing page, theme, or frontend template candidates, include both the repository URL and the live preview or demo URL for every serious candidate; when no preview is available or verified, state that and downgrade the candidate. Never answer with only links, Stars, or popularity rankings, and never write "common GitHub pattern" without linked evidence. When network or `gh` access is unavailable, state that GitHub research could not be performed and mark the recommendation local only. Partial results report what was found and what could not be verified; errors are never swallowed and the done bar is never pretended to hold.
